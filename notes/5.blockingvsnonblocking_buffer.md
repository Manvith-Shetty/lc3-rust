One more thing I have observed was this. For `read_memory` in case of MMIO we had to check for keyboard data in that KSBR is a status check. 
We can do 
```
fn poll_key() -> Option<u8> {
    let mut buf = [0u8; 1];
    std::io::stdin().read_exact(&mut buf).ok()?;
    Some(buf[0])
}
```
As this is a blocking way of reading the data into the buffer coz of `read_exact` which waits till it gets the value which is useful for case like GETC or IN Trap codes.

But incase of KSBR status check I need it immediately as its a status check.

What exactly happens in rust's BufReader
1. GETC calls stdin().read_exact(1 byte)
2. underneath, BufReader issues read(0, buf, 8192) sys call and pulls 8192 bytes into userspace (Kernal mode -> user mode)
3. it hands one byte to GETC and keeps 8191 (Next time if u ask more its just a memcopy)
4. poll_key calls select(fd 0) (a kernel call) → nothing readable → reports "no key waiting"

select(file descriptor) can see only the KERNEL QUEUE.
(FILE DESCRIPTOR: a non-negative integer that acts as a per-process handle to an open input/output stream. stdin is 0)

     keystroke / pipe write
              |
              v
     +--------------------+
     |   KERNEL QUEUE     |   <-- select() can see ONLY this
     +--------------------+
              |  read(0, buf, 8192)   <-- one syscall, slurps everything available (actually transfers data from fd to memory)
              v
     +--------------------+
     | BufReader (8192 B) |   <-- plain memory inside your process
     +--------------------+
              |  .read_exact(&mut one)   <-- no syscall, just a memcpy
              v
          your 1 byte

- So Rather in different cases (GETC and IN reading from blocking buffer but poll_key reading from non blocking kernel queue for status check is a bad idea) reading different queue which causes inconsistency like Thousands of keystrokes buffered and the VM swears the keyboard is idle.

- So we will not use buffered approach. Rather the below
1. Read one byte straight from kernel as kernel queue is the only source of truth.
2. ask kernel directly with select if the byte is available right now with no timeout.
3. now poll will use the above two functions.
